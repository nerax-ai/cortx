Ideation: Cortx Agent Core 设计校准

这份文档评估 cortx 当前核心是否足够优雅、简洁、可扩展，并提出让它成为未来所有 Agent 形态共用核心的方向。重点不是把所有能力塞进 core，而是把 core 必须承诺的契约讲清楚。

date: 2026-06-29 topic: cortx-agent-core focus: 通用 Agent core 需求与设计优雅性 mode: repo-grounded
8.0/10当前作为轻量 Agent framework 的成熟度
7.2/10当前作为“所有 Agent 共用核心”的完成度
9.3-9.5/10补齐本文前四项和 conformance 后的合理目标

Grounding Context

cortx 已经有一个很好的最小核心：agentLoop() 是 async generator，Cortx 类能 headless 运行，AgentEvent 给 TUI/Web/Server 共享事件流，Tool 和 CortxPlugin 把工具与横切逻辑隔离出来，agent 工具把 sub-agent 作为普通工具挂进系统。这些方向本身是优雅的。

当前问题不在“设计错了”，而在“契约还不够硬”。packages/core/src/loop.ts 已经增长到 552 行，同时承担模型流解析、消息持久化、重试、overflow、auto-continue、tool hook、并发调度、steering、abort 等职责。它仍然可读，但未来要加 timeout、permission、capability registry、named agents、resume/replay 时，会继续向同一个函数里塞。

@cortx/sdk 的公共契约目前很小：Tool、ToolContext、ToolResult、SideEffects、CortxPlugin 和 AgentEvent。这是好事，但也暴露了缺口：inputSchema 目前只声明不验证；sideEffects 能调度并发，但没有一等 permission/approval 语义；ToolContext 没有 AbortSignal、capability scope、message context、policy decision 等运行时事实。

文件工具说明了安全边界的现状：read/write/edit/ls 基本使用 resolve(cwd, path)，没有 workspace containment；edit 只检查 includes(oldText)，再替换首个匹配，没有唯一性保障。这些不是“代码工具的小 bug”那么简单，它们提示 core 需要定义能力、权限和作用域的统一语义。

外部基准也指向同一个方向。OpenAI Agents SDK 把 agent loop、tools、guardrails、handoffs/sessions、human-in-the-loop、tracing 作为运行时关键能力，且仍强调少量 primitives。LangGraph 把 durable execution、streaming、human-in-the-loop、persistence 定义为长运行 stateful agent 的底座。Vercel AI SDK 的 tool calling 文档把 schema validation、approval、multi-step、step hooks、abort signal 和 typed tool errors 做成常规工具生命周期能力。也就是说，现代 Agent core 的竞争点不是“是否能调用工具”，而是这些工具和步骤是否有稳定、可组合、可恢复的契约。

总体判断：当前设计方向合理，甚至比很多大而重的 agent runtime 更有长期潜力。但它还不是“所有大/小 Agent 都能复用”的 9.5 分核心。要继续改 cortx，优先改 core contract，而不是优先堆更多工具或 UI。

Ranked Ideas

  • 1. AgentKernel phase pipeline, with current API kept simple
  • 2. Runtime policy and capability layer
  • 3. Typed tool lifecycle protocol
  • 4. AgentSpec and named-agent registry
  • 5. Event-sourced session, checkpoint, and replay contract
  • 6. Core conformance suite across tiny and large agents
1

AgentKernel phase pipeline, with current API kept simple

Axis: Core loop / kernel contract Confidence: 92% Complexity: Medium

Description: 保留现在好用的 Cortx.run() 和 agentLoop() facade，但内部把 loop 拆成稳定 phase：prepare turn、transform messages、invoke model、decode assistant output、decide continuation、authorize tools、execute tools、apply tool results、recover/finish。phase 不需要变成复杂 graph，只要是清晰的 pipeline contract。

Basis: direct:loop.ts 当前同一函数覆盖 stream parsing、retry、overflow、auto-continue、tool hook、并发工具调度和 steering/abort；已有插件 hook 说明项目偏好可插拔横切逻辑，但 phase 级插入点还没有形成公共模型。

Rationale: 这是从 8 分向 9.5 分靠拢的根改动。它不追求重写架构，而是把已经存在的隐式阶段显式化。这样 timeout、retry、circuit breaker、quota、trace、permission、human-in-the-loop、context compaction 都能挂在正确 phase，而不是继续侵入 loop.ts。

Downsides: 需要小心避免“抽象比原来更重”。正确做法是先抽内部 phase 和 conformance，不急着公开一个庞大插件 API。

2

Runtime policy and capability layer

Axis: Tool runtime safety Confidence: 90% Complexity: Medium

Description: 在 core 层定义 PolicyDecision 和 CapabilityScope：allow、deny、ask、defer；workspace roots、read/write/destructive/network/shell/MCP/browser 等能力；headless 策略；审批事件和回答事件。UI 只负责呈现和收集答案，core 负责工具是否可执行的统一语义。

Basis: direct:SideEffects 已经存在并用于并发调度，但 tool.execute.before 只能 skip，TUI askUser 仍默认 yes，代码工具没有 workspace containment。外部 AI SDK 已把 sensitive tool approval 作为工具执行常规流程。

Rationale: 如果没有这一层，未来每个工具、skill、server、TUI 都会各写一套安全判断。小 Agent 需要“默认只读/无需打扰”的轻策略，大 coding agent 需要“写入前确认/危险命令阻断/指定 workspace”的强策略，它们应该共享一个 core policy contract。

Downsides: 需要设计默认策略，避免开发时过度弹窗；同时要保证 headless/server 场景不会因为缺 UI 卡死。

3

Typed tool lifecycle protocol

Axis: Tool runtime safety Confidence: 88% Complexity: Medium

Description: 把工具生命周期从“JSON.parse 后 execute”提升成协议：schema validation、typed validation error、optional repair feedback、streaming/progress、abort signal、tool timeout、structured result、tool-error part、result budget/provenance。ToolContext 增加 abortSignal、messages/context、capability scope 和 policy facts。

Basis: direct/external:Tool.inputSchema 当前存在但未验证；runToolCall() 中解析输入后直接执行；AI SDK 文档把 strict/inputSchema、InvalidToolInputError、tool-error、abort signal、onStepFinish 等作为工具调用基础设施。

Rationale: 这个方向直接服务“小 Agent 复用 core”的诉求。一个只需要提示词和几个函数的小 Agent，不应该被迫写自己的校验、错误反馈、取消逻辑；大型 Agent 也需要同一套协议来支撑 shell、browser、MCP、sub-agent、workflow tool。

Downsides: 需要选择验证库或抽象 schema adapter。也要处理旧工具兼容，不能一次性要求所有工具改写。

4

AgentSpec and named-agent registry

Axis: Agent composition Confidence: 87% Complexity: Medium

Description: 定义一个数据化的 AgentSpec：name、instructions/system、model preference、tools/capabilities、policy profile、memory/session adapter、maxIterations、background/concurrency、metadata。Cortx 可以从一个 AgentSpec 创建小 prompt agent，也可以从 named-agent registry 启动角色 agent。现有 sub-agent-as-tool 继续保留，只是能按名称加载角色定义。

Basis: direct:现有 Cortx 构造器接收 config/tools/plugins，agent 工具只能启动通用 sub-agent，Compound Engineering compatibility 文档已经明确需要 agent definitions、agent set、model inherit、tool scope 和 named dispatch。

Rationale: 这是满足用户例子“很细小场景，只需要一份提示词并使用一些功能的 Agent 也能复用核心”的关键。小 Agent 是 AgentSpec 的最小实例；大 Agent team 是多个 AgentSpec 的组合。core 不需要知道 Compound Engineering，但需要知道 named agent 这种通用资产。

Downsides: 容易过度配置化。第一版应只覆盖真正已有需求：prompt/system、tools/capabilities、model preference、limits、background、named registry。

5

Event-sourced session, checkpoint, and replay contract

Axis: State and observability Confidence: 85% Complexity: Medium

Description: 把 AgentEvent 明确变成 core 的审计日志和恢复输入：每个 turn、tool call、policy decision、approval、checkpoint、error、usage 都能记录；session 可以从 checkpoint 恢复；TUI/Web/Server 共用同一套 replay/serialization 语义。当前 AgentStore 继续作为投影层，而不是事实源。

Basis: direct/external:CortxSession、AgentStore 和 server SSE 已经围绕 AgentEvent 工作，但 TUI auto-save 只在 done/error；LangGraph 将 persistence、fault tolerance、interrupts/time travel 和 observability 作为长运行 agent 的核心能力。

Rationale: 可恢复和可调试是大 Agent 的生命线，也是小 Agent 嵌入应用后的生产要求。事件流已经存在，下一步不是另起状态系统，而是把事件、checkpoint、session projection 的职责边界定清楚。

Downsides: 事件 schema 一旦公开就需要版本化和兼容策略。需要区分“用户可见 transcript”和“运行时事实日志”，避免泄露敏感工具输入。

6

Core conformance suite across tiny and large agents

Axis: Capability and skill ecosystem Confidence: 84% Complexity: Low-Medium

Description: 建一个 core conformance suite，覆盖同一核心在不同规模下的行为：纯 prompt agent、prompt+single tool、multi-step tool agent、permission ask/deny、read-only parallel、write ordering、abort propagation、context overflow recovery、sub-agent/named-agent、server SSE session、resume/replay。

Basis: direct:当前仓库已有 loop.test.ts、loop-parallel.test.ts、agent-background.test.ts、server/session/TUI store 测试，但缺少跨 package 的“同一 core contract 必须成立”的测试矩阵。此前 Synax 的经验也说明，集成层没有断言时，协议正确性容易退化成人工看日志。

Rationale: 这是重构安全网。没有 conformance，就不应该大拆 loop.ts；有了 conformance，后续改 kernel、policy、tool lifecycle、AgentSpec 都能知道是否破坏了小 Agent 或大 Agent 的共同语义。

Downsides: 需要先定义“核心契约是什么”，否则测试会变成当前实现的快照。它应跟随前几项契约设计一起落地。

Rejection Summary

#IdeaReason Rejected
1直接把 cortx 改成 LangGraph 风格 graph runtime会牺牲当前最有价值的轻核心优势。cortx 应该学习 durable execution 和 state contract，不必复制 graph abstraction。
2只继续小修 loop.ts，不改内部结构短期省事，但 timeout、approval、capability、resume、trace 会继续堆在同一个函数里，长期不够 9.5 分。
3把 memory、planning、browser、workflow 全部做进 core方向太重。core 应定义 session/memory/capability 插槽和事件，不应该拥有所有具体策略。
4把 Compound Engineering 做成特殊内置分支违背通用 core 目标。正确抽象是 skill pack、named agents、capability mapping，而不是某个插件专用逻辑。
5为小 Agent 单独做一套 mini runtime会分裂生态。小 Agent 应是 AgentSpec 的最小配置，而不是第二套核心。
6把 sub-agent 升级为 core 特权 primitive现有 sub-agent-as-tool 方向是对的。需要补 named registry、policy、session，而不是让 sub-agent 脱离工具协议。
7先做大型 UI/Web IDE 再回头整理 core会把外层体验绑定到不稳定内核。先稳定 core contract，UI 才有可靠事件和能力语义可用。
8直接采用 Vercel AI SDK 或其他 runtime 作为核心可借鉴 schema、approval、abort、step hook 等模式，但 cortx 的目标是 provider-agnostic、skill/plugin-first、coding-agent-capable，不适合直接换核。
9只扩充更多 plugin hookshook 数量不是核心问题。缺的是 phase、policy、tool lifecycle、session 这些 typed contracts；没有 typed contract 的 hook 很快会变成约定俗成的字符串 API。
